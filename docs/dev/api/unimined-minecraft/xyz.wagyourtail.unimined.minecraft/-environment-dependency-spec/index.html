EnvironmentDependencySpec

class EnvironmentDependencySpec

The receiver of an environment's dependencies { } block — a scoped syntactic lift over the environment's existing dependency buckets (KMP source-set-dependencies style). Every verb resolves the configuration the env's source set already owns and adds the notation to it; no new resolution machinery exists behind the block, and the string configuration names remain fully functional alongside it.

Vocabulary:

  • implementation/compileOnly/runtimeOnly — the source set's ordinary java buckets (implementation for main, <env>Implementation for named envs). Non-mod jars on these pass through un-remapped, like the global dependencies { } block.

  • api — materialized on first use where Gradle doesn't create it: api exists only for main under java-library, and custom source sets have no <env>Api bucket at all. First use creates the bucket and wires <env>Implementation.extendsFrom(<env>Api) — java-library-equivalent semantics (compile+runtime visible in-dev), which unimined's publish wiring then carries in the env's api-elements channel like any existing <env>Api.

  • modApi/modImplementation/modCompileOnly/modCompileOnlyApi/ modRuntimeOnly/modLocalRuntime — the env's mod buckets: mod jars remapped from the mod source namespace into the dev namespace, loom-parity semantics. modImplementation is compile+runtime in dev and publishes at runtime scope only; modApi is the same in dev but publishes at api (compile+runtime) scope — the compile-visible-transitive bucket. modCompileOnly is compile-classpath-only — never on runtime classpaths, never published; modCompileOnlyApi is the same in dev but publishes at compile (api) scope. modRuntimeOnly is runtime-only in dev and publishes at runtime scope; modLocalRuntime is runtime-only in dev and NEVER published — local-launch-only mods.

  • include — the jar-in-jar embed bucket. NOT a classpath dependency: entries ship inside the production jar but are never compiled or launched against — declare modImplementation (or implementation for library jarjar deps) alongside when dev runs need the contents.

Dependency notation passes straight through to the project's org.gradle.api.artifacts.dsl.DependencyHandler, so every shape the global block accepts (coordinates, maps, project(...), files(...), providers) works here. Exotic per-dependency configuration ({ transitive = false }, capability tweaks) has no scoped twin — declare it on the string configuration name instead.

fun api(notation: Any): Dependency?

Api dependency of this environment's source set — api / <env>Api, materialized on first use. Gradle creates api only for main under the java-library plugin and never creates <env>Api for custom source sets (there is no java consumable variant for it); unimined creates the missing bucket and wires <env>Implementation.extendsFrom(<env>Api), giving it java-library-equivalent in-dev semantics. Pre-creating the bucket is safe against a later java-library application (Gradle's own creation is tolerant), and unimined's dev-variant publishing already extends its api-elements channel from an existing <env>Api, so the dependency surface stays meaningful for consumers of the env's artifact.
