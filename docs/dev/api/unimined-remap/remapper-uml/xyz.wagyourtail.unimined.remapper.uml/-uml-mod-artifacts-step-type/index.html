UmlModArtifactsStepType

class UmlModArtifactsStepType : RemapStepType<ModArtifactsStepSpec>

The modArtifacts step backed by UniminedMappingLibrary's AsmRemapper — binary surface (RemapSurface.JAR) only.

Mod-jar metadata survives a pure namespace remap with source-namespace references still embedded: kotlin.Metadata class names, mixin annotation refs (method, target, injection args), mixin config paths, and ClassTransform/JarModAgent transformer refs. This step runs a second ASM pass with only the mod-artifact xyz.wagyourtail.unimined.mapping.remapper.asm.AsmExtensions enabled, resolving those embedded refs through the source→target tree. The class/member remap itself is run as identity (target→target): the jar's classes are already target-named, and re-applying the real source→target map renames any target-named class that textually collides with an unrelated source-namespace row (e.g. mojmap DedicatedServer → yarn MinecraftDedicatedServer, while yarn has its own DedicatedServer) — producing duplicate output entries. The extensions still see the real source→target ExtensionContext, which is what their embedded-ref resolution needs.

Engine-agnostic by construction: appended to the JAR pipeline after remap regardless of which engine performed it (a remap("tiny") override gets identical treatment), and to remapped dependency views, so mod deps get mixin refmaps for the dev runtime. Resource-gated — MixinExtension and ClassTransformExtension only load when the jar carries their resources.
