MavenCoords

@JvmInline
value class MavenCoords(val value: String)

group:artifact:version[:classifier][@extension] coordinate string — the identifier loaders use when selecting embedded (jar-in-jar) candidates. The loaders' matching semantics live in ResolvedArtifactResult.getCoords: it constructs these from the variant's component id, resolved capabilities, and file-name classifier detection — the same inputs forge/fabric first-party tooling reads, so embedded ids line up. The getters here parse the string form (Gradle g:a:v:c@e notation) for DSL-facing uses like include("g:a:v") lookups.

RunGroupModel

open class RunGroupModel @Inject constructor

Cross-project run classpath-group model — one instance lives on the rootProject as the uniminedRunGroups extension. Each project's environment binding contributes its own projectPath:environmentId entry at configuration time; consumers read the model at execution, when every contribution is present regardless of project evaluation order. This replaces the gradle.projectsEvaluated recompute previously needed to see sibling projects' source sets and loader specs — a lifecycle hook configuration-cache builds should not need.

dependencyNotationPredicate
Link copied to clipboard
fun dependencyNotationPredicate(notation: String, context: String): (Dependency) -> Boolean

group:name[:version] DSL notation → a Dependency predicate — the shared parser behind the forceRemap verbs on MinecraftEnvironment and RemappedViewSpec. A two-segment notation matches any version of the module; a third segment pins it. Anything else — a missing name ("foo"), blank segments (":", "g:"), or extra fields ("g:n:v:classifier") — fails fast with an actionable error rather than crashing on index access or silently matching nothing.

getCoords
Link copied to clipboard
fun ResolvedArtifactResult.getCoords(): MavenCoords

Resolved artifact → MavenCoords, identical to forge/fabric first-party tooling: the module component id wins, but a resolved capability whose coordinates differ (relocated/shadowed variants) overrides it, and a <artifact>-<version>-<classifier>.<ext> file name contributes the classifier. Keeping this byte-for-byte is what makes the ids of jar-in-jar dependencies match the loaders' candidate selection.
